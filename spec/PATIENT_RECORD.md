# 太乙枢机个人病历最小契约

- 状态：2026-09-03 已确认并进入实现
- Schema：[`case_record.schema.json`](case_record.schema.json)
- 正式分析契约：[`MACHINE_CONTRACT.md`](MACHINE_CONTRACT.md)

本契约只保存个人 Agent Skill 进行实际病例和同案复察所需的事实、轮次、实际
处方、治疗反应与正式结果链接。它不是完整病历系统，也不复制正式分析全文。

## 1. 两层内容

`patient_record` 分开保存：

- **事实层**：用户原话、当前可确认事实、含混事实、用户主动提供但不进入中医
  推理的外部信息、医者既有意见、实际处方、治疗反应和明确更正；
- **复察解释层**：红方与必要 Stage C 后已经收敛的 R0、R1 纵向摘要、与上一轮
  的变化摘要、未解边界，以及对应正式 run/result 的文件链接。

完整 R0、R1、R2、红方和 Stage C 仍只存在 `committed_analysis` 中。病历中的
R0／R1 摘要是上一轮正式判断，不是患者事实，也不是下一轮预定结论。

## 2. 写入顺序

1. 新建病例并追加一份本轮事实完整快照；复察轮次以 `parent_turn_id` 明确连接
   同案上一轮，不按文本相似度猜测。
2. 尚未绑定正式结果的最新轮次可以带更正说明原子修正；已经绑定正式结果的轮次
   不原地改写，事实更正另建新轮次，保留旧分析的历史身份。
3. 正式主链使用本轮权威输入和一份冻结的 `case_snapshot`。
4. 正式分析完整提交后，宿主在同一上下文形成简短的最终 R0／R1 纵向摘要，
   再把 run/result 绑定回本轮。绑定失败不改写医学结果，可以重试绑定。
5. 模型或提交失败时，患者事实可以保留，但不写入分析绑定和复察解释层。

## 3. 冻结快照与职责分发

`case_snapshot` 只从明确父轮生成，并绑定当前 `case_id`、`turn_id` 和
`parent_turn_id`。它从父轮正式结果与病历解释层抽取一次必要内容，供输入锁
冻结；不把整份病历或全部历史装入模型。

角色制包按职责投影同一快照：

- R0：父轮最终 R0 纵向摘要，用于判断关系延续、转变或失效；
- R1：父轮最终 R1 纵向摘要、上一正式结果和三日预测，作为历史判断与回验材料；
- R2：上一实际／正式方、上一正式结果、三日预测和执行边界；
- 红方与必要 Stage C：上述完整有限快照，以及本轮完整主体结果。

当前轮次的已确认事实和含混事实来自本轮权威输入。完整用户原话继续保存于病历
与正式记录；病例角色不自动接收 `external_context`，也不把体系外信息变成中医
事实或裁决框架。

## 4. 状态与非范围

简单状态文件只登记病例文件路径、当前激活病例和一个写时复制沙盘，不再复制
每轮分析与权威输入作为第二份病例事实来源。

本契约不建立数据库、账户、权限、自动病例匹配、多人并发、事件流、版本树、
任务队列、完整检查化验系统、逐条病机谱系或第二套医学结论。可读病历页面如需
生成，只能是 `patient_record` 的确定性投影，不能成为另一份手工维护权威。

## 5. 机器边界

机器只校验病例／轮次身份、同案父轮、字段形状、绑定的 run/result 与正式记录
一致、已绑定轮次不可原地改事实、快照只来自明确父轮以及写入原子性。机器不判断
事实抽取是否完备、R0／R1 摘要是否正确，也不从症状、药名或既往结果推导病机。

# 太乙枢机最小机器契约

- 状态：2026-09-03 正式运行与个人病历快照边界已确认
- Schema：[`analysis.schema.json`](analysis.schema.json)
- 正反例：[`analysis_examples.json`](analysis_examples.json)
- 硬边界校验：[`../tools/analysis_contract.py`](../tools/analysis_contract.py)

本契约只描述个人 Agent Skill 一次运行可以完整提交的最小记录，以及一次没有
提交医学结果的失败。它不定义中医答案，不把 R0—R2 映射成固定模型调用，也不
保存层间摘要或逐角色来源图。

病例长期事实另由 [`PATIENT_RECORD.md`](PATIENT_RECORD.md) 和
[`case_record.schema.json`](case_record.schema.json) 承载；它们不扩张本分析
Schema，也不复制完整 R0—R2 或红方正文。

已有正式结果后的普通解释不产生本契约记录。一个写时复制沙盘保存假设方剂，
但不产生正式病例轮次，也不能作为后续正式结果的父轮；用户把假设变成实际处方
或正式结论时，以新的权威输入进入正式主链。本契约不新增“直接回答”或“沙盘
分析”任务类型。

## 1. 两种互斥结果

`committed_analysis` 表示一次完整提交。它保存不可变输入快照、实际形成的职责
正文、少量直接采用的短原文、结果身份和简洁调用日志。`run_failure` 只保存错误
身份及可选的上一可用运行 ID；失败信封不能携带推理、方药或三日结果。

提交程序在临时位置一次装配并校验，全部通过后原子替换目标文件。失败不能覆盖
上一份正式结果，也不能由 Python 补写一份医学答案。

## 2. 不可变输入与对象身份

`input.raw_text`、主对象、病例／轮次，以及角色为 `input`、`reference`、
`mentioned` 的方剂属于输入所有者。提交校验必须与模型运行前保存的
`authoritative_snapshot` 逐值比较，不能让同一份模型输出自证守恒。

R0 开始前先对权威快照及当前对话明确指定的可选上一正式记录生成一个轻量哈希
锁。每个角色制包和最终提交都核对同一把锁，哈希只存在运行侧车文件，不进入
Schema、角色输入或读者正文。锁定后需要改动身份、事实、方剂组成或顺序时，
本次尝试失效，必须重新冻结并重做全部职责，不能让旧角色结果依附到修改后的
输入上。

方剂不要求名称。每味只使用 `raw_text`、`name`，以及实际出现时的 `amount`、
`unit`、`preparation`；组成顺序保留。先煎、后下、冲服等原始表述留在对应
`raw_text`，方剂整体的剂型、制备和服用信息分别使用 `preparation_text` 与
`administration_text`，不为单味另造煎服字段。候选方、`R2 详细建议（待医师
复核）` 和写时复制沙盘使用独立 `formula_id` 与角色，不能成为输入方，也不能
互相冒充。

同一对话明确继续分析同一输入方，且显式组成没有增减、替换或改量，只补充
炮制、剂型或煎服信息时，沿用原 `formula_id`，新运行只产生新的 `run_id` 与
`result_id`。组成发生上述实质变化时才新建方剂身份。该规则复用现有 ID，不
增加方剂版本、父子谱系或依赖图字段。

只有病例与复察保存 `case_context`。复察使用同一 `case_id`、新的 `turn_id`
和明确 `parent_turn_id`；契约不按文本相似度猜测病例。
复察还必须在冻结时指定与 `case_id`、`turn_id`、`parent_turn_id` 一致的一份
`case_snapshot`。它由明确病历父轮及其正式分析确定性生成，只含父轮最终 R0／R1
纵向摘要、正式结果、三日、边界和实际／正式方。制包时 R0、R1、R2、红方与
Stage C 各自只取得职责需要的子集；不把父轮原话、`scope`、调用日志、完整来源、
候选／沙盘方、红方与 Stage C 过程或完整角色正文当作本轮结果。职责投影不调用
模型，也不保存第二套摘要文件。

`input.scope` 继续保存在权威快照和正式记录中，用于用户边界守恒；模型角色包
不把其模板化正文当作医学事实。经典与方剂角色直接读取当前 `raw_text`；病例与
复察角色读取当前主对象、已确认事实、含混事实、病例身份与方剂，完整原话继续
留在正式记录中。用户主动提供的体系外信息只保存在个人病历隔离字段，不自动
进入中医角色输入。

## 3. 职责结果与正式结果

`reasoning` 只保存实际发生的完整自然语言结果：每个角色只有 `text`，不保存
`handoff`、`evidence_ids` 或另一种摘要。经典解释至少有 R0；方剂、病例和复察
保存 R0、R1、R2 与隔离红方。只有红方发现实质冲突时才保存 Stage C。

R1 直接读取完整 R0，R2 直接读取完整 R0、R1；红方读取完整主体候选，Stage C
读取完整主体与红方结果。这些上下文关系由 Skill 装载和真实运行轨迹证明，不用
Schema 字段模拟。`calls` 只记录实际发生的宿主或红方职责；机器能核对成功职责
与已保存结果一致，不能证明隔离质量或医学推理质量。一次调用失败、被中断或
重启时，按实际结果保存该次 `failed` 记录；后续成功尝试使用新的 `call_id`，
不能用成功记录覆盖失败尝试。

Stage 0 仍可作为同一宿主调用已经承担任务理解的职责标签，但不对应独立角色
结果、packet、模型调用或可见推理步骤。契约不要求为了记录 Stage 0 增加调用。

新任务中的职责正文必须由当前输入实际形成。宿主不搜索记忆、历史运行或旧验收
样例来形成或核对本轮医学结论；旧角色正文、旧 packet、旧来源集和旧候选结果
不能作为本轮 R0—R2 或红方结果传入提交。只有当前对话明确继续同一方剂或激活
同一病例时，上一正式记录才作为冻结的身份与状态上下文；当前职责结果仍重新
形成。这一执行边界不增加 Schema 版本图或历史路径字段。

未解实质冲突使用自然语言字符串列表。实质冲突只指会改变核心关系、方剂主轴、
药物身份、来源身份、结果身份，或使当前条件性结论本身无法成立的问题。纯方剂
任务缺少只影响现实执行的煎煮参数、服用时点或患者事实，本身不进入该列表。
列表非空时，契约拒绝 `r2_pending_physician_review` 和任何
`formal_recommendation` 方剂。

纯方剂在显式组成守恒、条件性结论成立且没有未解实质冲突时，可以提交
`conditional_r2`；缺少现实煎服参数只限制 summary、risks 或 minimum_questions
中的执行边界，不要求自动改成 `reserved_opinion`。
`reserved_opinion` 或 `facts_or_evidence_insufficient` 用于上述实质问题确实使
条件性结论不能完整成立的情况。方剂、病例和复察的 Day 1／2／3 分别使用条件
预测、病例预测和复察预测身份；已经发生的变化只留在输入事实。

## 4. 短原文与最小来源校验

正式记录的 `sources` 只保存模型和读者真正需要的：

- `work_id` 与典籍名称；
- `kb/texts/` 文档路径；
- 起止行号；
- 逐字短摘录。

不保存模型综合“证据”、未取回占位证据、逐角色来源引用、内部证据编号，或在
每条来源中重复 `run_id`／`result_id`。未取回会限制结论时，角色和 outcome 用
自然语言说明。解释结论不伪装成直接引文，也不要求反复标明“模型综合”。

运行时每个职责使用独立的临时来源集，默认可以为空；某条来源只有在当前职责
真正采用时才进入其上下文，不能因上一职责已经取回就自动累计。契约不保存这些
临时集合，最终 `sources` 只是本轮各职责实际采用来源的去重并集。

校验器对每个直接来源只完成一次必要回读：按 `work_id` 核对清单中的典籍名称
和路径，读取 `kb/texts/`，核对正文 SHA、行号与短摘录。SHA 留在正文清单和证据
服务，不要求模型生成，也不重复写入医学记录。

## 5. 文字结果与后续扩展

默认正式输出是文字：顶部采用已经形成的最终 outcome，随后原样排版 R0、R1、
R2、红方和必要 Stage C，再显示任务适用的三日演化、未解冲突、风险、最小补问
与短原文来源。渲染器不调用模型重写职责正文，也不显示内部来源编号。

H5、图像和导出不属于默认提交的必填字段。用户明确要求后，扩展直接读取已经
提交的 `analysis.json`，并在自身输出中绑定同一 `run_id` 与 `result_id`；扩展
失败不修改或阻塞文字结果。本轮不在医学记录中预建 projection 图或异步队列。

## 6. 刻意不承载

本契约没有固定调用数、代理数、六维审计字段、逐句／逐药／逐图边谱系、来源
依赖图、事件全集、评分、投票、任务队列、数据库、多人状态、模型网关、商业
恢复流程、H5 第二套医学状态或整章典籍。

本契约也不保存宿主的“直接回答／单沙盘／正式主链”语义路由结果；是否进入
正式主链由宿主理解当前用户动作后决定，不由 Schema 或关键词裁决。

机器测试不判断一气、阴阳、证机、方义、红方攻击或 Stage C 医学质量，也不以
正则、词表、药性表或固定栏目代替模型语义。历史作品和旧 packet 保留为运行
证据，不要求通过本次不兼容契约，也不能直接充当新任务的职责结果。

机器可以核对同方补充信息时 `formula_id` 是否连续、当前职责 packet 是否只含
调用者明确传入的来源，以及 `conditional_r2` 是否在缺少现实执行参数时仍为
Schema 允许的合法结果；也可以核对输入锁、复察父记录身份和锁定后不接受补改，
不能据此判断卦象、阴阳或方义是否正确。

个人病历契约还可以核对：轮次按同案最新父轮追加；已经绑定正式分析的轮次不能
原地改事实；分析绑定的 case/turn/run/result 与正式记录一致；复察快照只来自
明确父轮；A→B→A 激活不串案。它不能判断事实抽取、医者意见或 R0／R1 纵向摘要
的中医质量。
